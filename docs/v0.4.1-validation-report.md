# Perf instrumentation — validation report (release v0.4.1)

Release **v0.4.1** is the **perf-instrumentation infrastructure release**. It adds a layer-by-layer latency capture surface to the plugin (thread-local rdtsc rings, per-method binary files, offline analyser) and a side-by-side comparison harness against MariaDB+TidesDB. No engine optimisations ship in this release — the deliverable is the **fact base** that future optimisation work will key off. The bundled engine is unchanged from v0.4.0 (still TidesDB **v9.3.2**, still shipped unpatched). Plan: [docs/superpowers/plans/2026-06-04-perf-instrumentation.md](superpowers/plans/2026-06-04-perf-instrumentation.md). Spec: [docs/superpowers/specs/2026-06-04-perf-instrumentation-design.md](superpowers/specs/2026-06-04-perf-instrumentation-design.md). See also [CHANGELOG.md](../CHANGELOG.md) and [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

## Perf-instrumentation surface added in v0.4.1

This release is **plugin-only**: the bundled TidesDB engine is byte-for-byte the v9.3.2 release we shipped in v0.4.0. Everything below is new plugin code under `plugin/` plus a new analyser at `tools/tidesdb_perf_analyze/` and a new harness at `bench/perf/`.

### Thread-local rdtsc ring buffer

Each MySQL session thread allocates a per-thread `TLS_Ring` (default 2^16 = 65,536 samples, runtime-configurable via `tidesdb_perf_ring_capacity_pow2`). A 24-byte `Sample` records `{method_id, thread_id, enter_tsc, exit_tsc}` packed with natural 8-byte alignment (`static_assert` enforces 24 bytes). The ring self-registers into a lock-free linked list (`g_rings_head`) on first use; the flusher thread walks that list without needing a global lock.

### `TDB_PERF_SCOPE(MethodId)` RAII macro

A 32-value `MethodId` enum covers the full plugin entry surface (`write_row`, `update_row`, `delete_row`, `index_read_map`, `index_next`, `index_prev`, `rnd_next`, `rnd_pos`, `external_lock`, `start_stmt`, `store_lock`, `commit`, `rollback`, `savepoint_*`, `open`, `close`, `info`, `table_flags_cache_init`, `create`, `delete_table`, the four inplace-ALTER virtuals, `serialize_row`, `deserialize_row`, `key_copy_to_comparable`, `pk_from_record`, `encrypt_row_into`, `decrypt_row`). The macro captures `__rdtsc()` on construction; on destruction it short-circuits if `g_capture_active` is `false`, or pushes a 24-byte `Sample` into the calling thread's ring. With capture off the overhead is two rdtsc reads + one atomic-load — measurable below 50 ns per scope on the host above.

### Background flusher + per-method `.bin` files

A single flusher thread pinned to CPU 0 wakes every `tidesdb_perf_flush_interval_ms` (default 1000 ms, smoke runs use 200 ms), walks `g_rings_head`, bucket-sorts samples by `method_id`, and `pwritev`s each bucket to its method's append-only `.bin` file (`<thread_id>-<NN>-<method_name>.bin`). On `perf::init()` the flusher calibrates the TSC frequency with a 20 ms `std::chrono::steady_clock` spin and writes the calibration plus host metadata to `<thread_id>-meta.json`. On wrap (ring overflow) the first occurrence is always logged; subsequent wraps are rate-limited to one per 60 seconds via an atomic last-log timestamp.

### Four perf sysvars

- `tidesdb_perf_capture` — `BOOL`, default **OFF**. The kill-switch; flips `g_capture_active` at runtime with no plugin reload.
- `tidesdb_perf_output_dir` — `STRING`, default `/var/lib/mysql/tidesdb-perf` (`PLUGIN_VAR_MEMALLOC` so the value survives runtime mutation). Resolved on `perf::init()`; warns and continues if the directory is not writable.
- `tidesdb_perf_ring_capacity_pow2` — `INT`, default **16** (`PLUGIN_VAR_READONLY` — sized once per thread on ring alloc).
- `tidesdb_perf_flush_interval_ms` — `INT`, default **1000**. Runtime-mutable; the flusher reads the value each iteration.

All four are gated under `#if TIDESDB_PERF`; with the default build (`TIDESDB_PERF=0`) `SHOW VARIABLES LIKE 'tidesdb_perf%'` returns nothing.

### Offline analyser

`tools/tidesdb_perf_analyze/__main__.py` (Python 3, numpy) parses the `.bin` files (`struct.pack('<BBH4xQQ', ...)` per sample), aggregates per-method `calls / total_ms / mean_us / p50 / p95 / p99 / max`, and emits a markdown report sorted by total time. `--compare A B` produces a side-by-side diff against a second capture directory (intended for MySQL vs MariaDB comparisons). 2/2 pytest cases pass.

### Integration harness

`bench/perf/run-perf-capture.sh` wraps `bench/hammerdb/run-hammerdb.sh` to:
1. Tag `tidesdb/mysql:9.7-perf` as `tidesdb/mysql:9.7` for the run (saved/restored on exit).
2. Force the perf sysvars ON via `DB_EXTRA_ARGS`.
3. Mount `/tmp/perf-out` into the container.
4. After the run, docker-mediate copy the `.bin` files out of the volume (mysql uid 999, mode 640) and chown to the invoking host uid:gid.
5. Run the analyser, write `report.md` next to the `.bin` files.

`COMPARE=1` extends the same flow against `sut-mariadb-tidesdb:9.3.0-perf`. The TideSQL perf-instrumentation patch (`docker/patches/tidesql/0001-perf-instrumentation.patch`, 880 lines) ports the same `Sample` / `TLS_Ring` / `PerfScope` / 30-call-site surface into MariaDB's `ha_tidesdb.cc`. Building the MariaDB+TideSQL perf SUT image is **deferred to v0.5.0** (see "Deferred" below).

Observations the team can mine in the v0.5.0 cycle:

- `write_row` median is 1.69 μs but **max is 72 ms** — a long compaction-stall tail that dominates the total. p99 is 17 μs, so the tail is rare but heavy.
- `index_read_map` p95 (44.7 μs) is **8× the p50** (6.1 μs); the read hot path has a meaningful long tail too.
- `pk_from_record` is the **most-called** method (6.36M calls, vs `write_row`'s 5.29M) but the cheapest (mean 0.19 μs). Optimising it would change the noise floor but not the wall-clock budget.
- `external_lock` fires 2.9M times for 1.6 s of total CPU; that's plumbing overhead from the per-statement lock acquire path.
- `create` averages 12 ms per call (11 calls = the 10 TPC-C tables + bench init). Schema-build dominates wall-clock during build but doesn't appear in steady-state OLTP.

All other methods together account for ~9 s out of the ~124 s of perf-attributed CPU time across the 3-min run — well over 80% of plugin CPU lives in `write_row` and `index_read_map`.

## Deferred to v0.5.0

The following items were on the v0.4.1 spec but are explicitly **not** in this release:

- **MariaDB+TideSQL perf SUT image** (`sut-mariadb-tidesdb:9.3.0-perf`). The TideSQL perf patch is committed (`docker/patches/tidesql/0001-perf-instrumentation.patch`, 880 lines), but actually applying the patch on top of the v9.3.0-aged TideSQL fork + building a Dockerized SUT is its own integration milestone. `COMPARE=1` paths in the harness will exit cleanly without it.
- **Engine-side optimisations.** v0.4.1 ships the fact base. The hotspots above are the entry points for v0.5.0 work; nothing in this release changes engine behaviour.
- **TideSQL perf sysvars.** The patch wires the `TDB_PERF_SCOPE` call sites and ports `Sample`/`TLS_Ring`/`PerfScope` into MariaDB, but does **not** wire the four perf sysvars; the harness will force-enable capture by other means when the side-by-side run lands.
