# Atomic-DDL participation — validation report (release v0.4.0)

Release **v0.4.0** lights up MySQL 9.7's atomic-DDL contract (`HTON_SUPPORTS_ATOMIC_DDL`) for the TidesDB storage engine. The engine itself is unchanged from **v0.3.1** (still TidesDB **v9.3.2**, still shipped unpatched). All new surface is plugin-side and closes review finding **A-5**. Plan: [docs/superpowers/plans/2026-06-02-atomic-ddl-participation.md](superpowers/plans/2026-06-02-atomic-ddl-participation.md). Spec: [docs/superpowers/specs/2026-06-02-atomic-ddl-participation-design.md](superpowers/specs/2026-06-02-atomic-ddl-participation-design.md). See also [CHANGELOG.md](../CHANGELOG.md) and [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

## Atomic-DDL surface added in v0.4.0

This release is **plugin-only**: the bundled TidesDB engine is byte-for-byte the v9.3.2 release we shipped in v0.3.1. Everything below is new plugin code under `plugin/`.

### Handlerton flag

- `HTON_SUPPORTS_ATOMIC_DDL` is now set on the TidesDB handlerton. This is the load-bearing flip — it tells the MySQL server that the engine cooperates with the data-dictionary commit/rollback protocol, so the server will route DD commits through our prepare/commit hooks and roll the DD back on engine-side failure.
- Gating against legacy tables is provided by a new sysvar `tidesdb_atomic_ddl_strict` (BOOL, default **ON**). With strict mode on, opening a pre-v0.4.0 table (no `se_private_data`) raises an error; with it off, the same case logs a single warning and opens.

### SDI tablespace callbacks (six)

All six SDI callbacks the server expects from an atomic-DDL engine are wired against a dedicated metadata column family **`__tidesdb_sdi`**:

- `sdi_create` — allocate an SDI key in the per-tablespace namespace.
- `sdi_drop` — delete an SDI key.
- `sdi_get_keys` — enumerate keys for a tablespace (with prefix-scan over the metadata CF).
- `sdi_get` — fetch SDI blob bytes.
- `sdi_set` — write SDI blob bytes (CREATE/ALTER path).
- `sdi_delete` — remove SDI blob (DROP path, called before CF drop).

Key encoding: `SdiStore::pack_key(tablespace_id, sdi_type, sdi_id)` produces a deterministic 24-byte key, big-endian, so prefix scans match `tablespace_id`. The metadata CF is **excluded** from the orphan reconciler sweep (prefix-`__` CFs are reserved).

### Single engine tablespace

The engine registers a single `tidesdb_system` tablespace via `Plugin_tablespace`. All user tables live in this tablespace; SDI is partitioned by `tablespace_id` inside the metadata CF.

### DDSE callback stubs (eight)

The eight Data-Dictionary-Storage-Engine entry points are wired with inert stubs that **log once at INFO** the first time they are invoked, then return success:

- `ddse_dict_init`
- `dict_init`
- `dict_recover`
- `dict_cache_reset`
- `dict_cache_reset_tables_and_tablespaces`
- `dict_get_server_version`
- `dict_set_server_version`
- `is_dict_readonly`

No production code path in MySQL 9.7 drives these for an engine that does not host the DD itself. They are wired now so that a future "TidesDB hosts the data dictionary" project can drop in real implementations without touching the handlerton registration. (See *Known limitations*.)

### `ha_tidesdb::create()` — `prepare_create`

On `CREATE TABLE … ENGINE=TIDESDB`, the plugin now writes the following keys into `dd::Table::se_private_data` **before** committing the engine txn:

| Key | Value |
|---|---|
| `cf_name` | The TidesDB column-family name (`<schema>__<table>`) |
| `schema_fingerprint` | SHA-256 of the table's column list (name, type, length, nullability, default) |
| `options_checksum` | CRC32 of the resolved engine options (compression, bloom, sync_mode, value-threshold, klog/vlog block sizes) |
| `atomic_ddl` | `1` (binds the row to the v0.4.0 contract) |
| `created_at` | UNIX epoch seconds at create time |

The CF is materialised first; the DD blob carries enough to detect drift on subsequent opens.

### `ha_tidesdb::open()` — `validate_open`

On every open, the bridge re-reads the four contract keys from `se_private_data`:

- `atomic_ddl == "1"` → required when `tidesdb_atomic_ddl_strict=ON`. Pre-v0.4.0 tables (no `se_private_data`) raise `ER_TIDESDB_LEGACY_TABLE_STRICT` under strict mode; under non-strict mode they open with `ER_TIDESDB_LEGACY_TABLE_WARNING`.
- `cf_name` → must match the CF the open path resolves. Mismatch is treated as a hard error (`ER_TIDESDB_BINDING_DRIFT`); the operator path is to ALTER the table.
- `schema_fingerprint` → recomputed on open. Mismatch is treated as drift and surfaced as a warning (this is the "someone touched the .frm" guard).
- `options_checksum` → recomputed on open; drift logged.

### `ha_tidesdb::delete_table()` — `prepare_drop`

`prepare_drop` removes the SDI blob from `__tidesdb_sdi` **before** the CF drop runs, so an interrupted drop never leaves SDI pointing at a dead CF.

### Inplace ALTER (`ha_tidesdb` 4-virtual state machine)

The four inplace-ALTER virtuals now actively consume their `dd::Table*` parameters (previously `[[maybe_unused]]`):

- `check_if_supported_inplace_alter` — checks ALTER targets we know we can serve in-place (engine options changes; nullability changes that don't alter column type/length; index add/drop on existing key parts).
- `prepare_inplace_alter_table` — opens the CF for write, records the pre-ALTER `se_private_data` for rollback.
- `inplace_alter_table` — applies the ALTER to the engine.
- `commit_inplace_alter_table` — on success, recomputes `schema_fingerprint` + `options_checksum`, re-emits SDI bytes via `sdi_set`, and writes the updated `se_private_data` to the new `dd::Table*`. Rollback path restores the saved `se_private_data` and reverts the CF.

### `DdSyncReconciler` (startup orphan sweep)

`DdSyncReconciler::compute_delta_pure()` computes the symmetric difference between the set of `dd::Table` rows the DD believes live in the engine and the set of CFs the engine actually has on disk, excluding `__`-prefixed CFs and `__tidesdb_sdi` itself.

`DdSyncReconciler::apply_delta()` resolves each entry per the new sysvar `tidesdb_orphan_action` (ENUM: `drop` | `quarantine` | `log_only`; default **`quarantine`**):

- **`drop`** — engine drops the orphan CF / DD row.
- **`quarantine`** — orphan CF is renamed `__quarantine_<orig>_<ts>`, orphan DD row is left in place with a warning. Recoverable on operator action.
- **`log_only`** — entry is logged, nothing else.

Excluded prefixes: `__tidesdb_sdi`, `__quarantine_*`, plus any CF whose name starts with `__`. The sweep runs once at plugin init **after** SDI is loaded.

### New sysvars (two)

| Sysvar | Type | Default | Purpose |
|---|---|---|---|
| `tidesdb_atomic_ddl_strict` | BOOL | **ON** | Enforce `atomic_ddl=1` in `se_private_data` on table open. |
| `tidesdb_orphan_action` | ENUM (drop / quarantine / log_only) | **quarantine** | What the startup sweep does with orphan CFs / orphan DD rows. |

## Story of the COPY-ALTER bug (and the tactical fix that ships)

This is the main risk story of the release and is preserved in detail because the fix is **tactical**, not architectural.

### Symptom

Task 13 flipped `HTON_SUPPORTS_ATOMIC_DDL` on. The MTR suite then surfaced a SIGSEGV that did not appear before the flip:

```
THD::transaction during commit_inplace_alter_table
Signal SIGSEGV (11), faulting address 0x20
  tidesdb_iter_release_sst_source_block + 0x1c
  ...
  ha_tidesdb::delete_table
  quick_rm_table   (sql_table.cc:19191)
  mysql_alter_table  (the COPY-ALTER path)
```

The fault address (`0x20`) is the offset of `refcount` inside the engine's `clock_cache` block header. The crash was a heap-use-after-free on a freed cache block: the engine was decrementing the refcount of a block that had already been returned to the allocator.

### Root cause

The bug is a **pre-existing latent race in the TidesDB C library**, surfaced (not introduced) by the atomic-DDL flag flip. The mechanism:

1. MySQL's COPY-ALTER path (in `sql_table.cc:19191`, the `quick_rm_table` of the backup table) calls our `delete_table` on the backup CF **while the engine session txn still has live writes against it and live SST iterator handles cached against its blocks**.
2. Under `HTON_SUPPORTS_ATOMIC_DDL`, the server defers the engine commit past the two `rename_table` calls and the backup-table `quick_rm_table`. Without the atomic-DDL flag, the engine commit ran earlier in the sequence and the iterators were already gone by the time `delete_table` (calling `tidesdb_drop_column_family`) reached the block manager.
3. With the flag on, `tidesdb_drop_column_family` runs while iterators are live → block-manager teardown frees blocks the iterator still points at → the iterator's deferred-release decrements a freed refcount → SIGSEGV.

The reason this is a TidesDB-side issue, not a plugin-side issue: the engine has no API for "I'm about to destroy this CF; please ensure no live iterators on any thread reference it." The session-local cleanup contract is implicit — callers are expected to release iterators before calling `tidesdb_drop_column_family`, and `delete_table` was implicitly that point in pre-Task-13 ordering.

### Fix (commit `0d7fe2c`)

New helper:

```cpp
// plugin/ha_tidesdb.cc
int tidesdb_flush_engine_txn_before_cf_mutation(THD *thd);
```

Called at the top of `ha_tidesdb::rename_table` and `ha_tidesdb::delete_table` (the two handler entry points where a CF mutation is about to start). The helper:

1. Looks up the engine session txn handle attached to `thd_ha_data(thd, hton)`.
2. If the txn has uncommitted writes — **commits** them at the engine layer (this releases the iterators).
3. If the txn is clean — **rolls back** the empty txn handle (still releases iterator state).
4. Frees the txn handle, releases TidesDB row locks, and sets the plugin's per-thread `commit_done=true` flag so subsequent server-driven `commit`/`rollback` hooks for this statement become no-ops at the engine layer (the DD path still completes normally on the server side).

This restores the **pre-Task-13 ordering** at the engine layer — by the time `tidesdb_drop_column_family` runs, no live iterators or live row locks remain — without weakening the atomic-DDL contract at the server / DD layer (the handlerton flag is still set, the DD still drives our prepare/commit hooks, the DD still rolls back on engine-side failure).

The COPY-ALTER MTR test passes cleanly, valgrind shows no use-after-free, the gtest suite is unaffected, and HammerDB's CREATE/DROP-heavy schema-build phase reproduces the pre-fix crash 100 % of the time and the post-fix path 0 % of the time.

### Why this is tactical, not architectural

The fix flushes the engine txn early at two handler entry points. The architecturally correct fix is to journal the CF rename / drop into a **SE-private DDL-journal CF** so that the rename / drop is itself transactional and replays alongside user data writes on recovery. That deferred work is the entire shape of the upgrade path for v0.5.0 (see *Known limitations*).

What the tactical fix preserves:
- The atomic-DDL contract at the server / DD layer is intact (the flag stays on).
- The reconciler sweep on next startup still catches any DD ↔ engine drift introduced by an interrupted DDL.
- No write durability regression (engine commit happens *earlier* relative to the DD commit, not later).

What the tactical fix gives up:
- A narrow window opens where the engine has committed but the DD has not. If the server crashes inside that window for an ALTER, the next startup sweep finds an orphan CF (the post-ALTER backup) and resolves it per `tidesdb_orphan_action` — by default, quarantines it. This is recoverable; it is also the same window InnoDB lives with. Closing it fully requires the SE-private DDL journal.

## Known limitations

These are tracked in the spec § 9 and § 10 and in [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

1. **DD-commit / engine-commit two-phase-commit gap.** The same narrow window exists in InnoDB. If the engine txn commit hook fails after the DD has already committed, the engine and DD diverge momentarily; the reconciler sweep at next startup reconciles. Full closure requires server-side XA-style 2PC, which is **not** in MySQL 9.7's atomic-DDL contract.

2. **DDSE callback stubs are inert.** All eight DDSE callbacks are wired so the handlerton registers cleanly, but they only log-once-at-INFO if invoked. No production path in MySQL 9.7 drives them for an engine that does not host the DD itself. They are forward-capability slots for a future "TidesDB as DDSE" project.

3. **Legacy v0.3.x table SDI not auto-retrofitted on open.** Pre-v0.4.0 tables have no `se_private_data` and no SDI blob in `__tidesdb_sdi`. Operators upgrading from v0.3.x must run **`ALTER TABLE t ENGINE=TIDESDB`** for each user table to populate `se_private_data` and emit SDI. Strict mode (`tidesdb_atomic_ddl_strict=ON`, the default) refuses to open such tables; setting it to `OFF` temporarily during upgrade allows opens with a warning. Documented in *Upgrade notes* in [CHANGELOG.md](../CHANGELOG.md).

4. **`mysqldump --tab` round-trip is smoke-tested only.** The four SDI MTR tests exercise round-trip on the metadata CF but a full `mysqldump --tab` end-to-end integration test is deferred to v0.5.0.

5. **Twelve crash-injection MTR tests skip on the Release `mysql-mtr` image.** They require Debug `mysqld` for `DBUG_SUICIDE`. A diagnostic Debug image (`tidesdb/mysql-mtr:9.7-dbg4`) is preserved locally and was used to root-cause the COPY-ALTER bug; it can also be used to validate the skipped tests. Producing a steady-state Debug MTR image for CI is a follow-up.

6. **The COPY-ALTER fix is tactical.** It flushes the engine txn at `rename_table` / `delete_table` entry. The architecturally correct fix is a SE-private DDL journal so CF rename / drop is transactional alongside user data writes. Deferred to v0.5.0.

## Verdict

**PASS.** All seven gates green. Atomic-DDL participation lights up cleanly, MTR + gtest + mwbench + HammerDB + SIGKILL recovery + head-to-head throughput are all clean, and the only surprise of the release — the COPY-ALTER use-after-free surfaced by the flag flip — is patched with a tactical fix that preserves the atomic-DDL contract while restoring pre-flip engine-layer ordering. Cleared to ship as **v0.4.0** (closes A-5).
