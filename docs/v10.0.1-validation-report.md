## Defects found and fixed during validation

Four v9 → v10 contract changes were found that **the compiler could not catch**:
the signatures are identical and only the meaning changed.

### 1. TTL was a silent no-op

`tidesdb_txn_put` took an absolute expiry in v9 and takes a lifetime in seconds
in v10. An absolute timestamp read as a lifetime is roughly 56 years, so no row
with a TTL ever expired. Found by `tidesdb_ttl`.

### 2. Iterator keys and values leaked — 12 GiB, OOM

`tidesdb_iter_key` returned a borrowed pointer in v9 (`*key =
iter->current->key`) and is documented in v10 as "newly allocated key the
caller frees". Thirty call sites kept reading the key correctly and leaking it,
`iter_read_current` — every row of every scan — worst among them.

On a WARE=1 TPC-C run the server went from 470 MiB to the 12 GiB container
limit and was SIGKILLed. Nothing reported it: `performance_schema` accounted
131 MB and `tidesdb_memtable_bytes` 92 MB, because a buffer the engine has
handed off is no longer the engine's to report, and an OOM-killed process
writes no log. It surfaced only as "Lost connection to MySQL server" from the
client.

Fixed with a scope guard at each site, since these sit in scan loops with
several early exits apiece. Note for anyone backporting: on TidesDB 9 freeing
these pointers would corrupt the heap.

### 3. Retrying a failed commit could not work

`maybe_bulk_commit` retried a failed mid-statement commit, on v9's contract that
the error came back "before marking the txn aborted ... so re-calling it is
safe". TidesDB 10 aborts first — every failure path past the write phase sets
`TDB_TXN_ABORTED` and leaves the registry. The retry therefore called commit on
a finished transaction, got `TDB_ERR_INVALID_ARGS`, and reported *that* instead
of the real cause. A conflict surfaced to operators as "invalid arguments".

### 4. Column-family names freed with the wrong allocator

`tidesdb_list_column_families` documents freeing with `tidesdb_free`; ten sites
used libc `free()`. The engine can be built against jemalloc, mimalloc or
tcmalloc, making that heap corruption — inert today only because the build
forces the system allocator. Found by auditing the v9/v10 doc contracts for
every engine function the plugin calls.

### Also fixed

- **Row counts excluded unflushed keys**, reporting `TABLE_ROWS` 0 and pushing
  the optimizer onto full scans; `DATA_LENGTH` read 0 for tables holding rows.
- **READ COMMITTED could miss a committed row**: a scan iterator was cached
  across statements and only re-seeked, which is correct for repeatable read
  and above and wrong for read committed.
- **Engine: conflict-free commits refused.** The reservation retirement floor
  counted the committing transaction itself and read a value maintained for the
  compaction GC floor, whose safe direction is the opposite. A single connection
  committing in a loop aborted against itself — 2 spurious conflicts per 1000
  transactions, 0 after. Carried as a patch and sent upstream.

## Open issue

**Concurrent bulk loaders take false conflicts and fail.** Several connections
bulk-loading at once hit `TDB_ERR_CONFLICT` on disjoint keys, because the
engine's reservation table refuses a hash collision as a conflict whenever the
colliding slot is newer than the oldest live snapshot — routine once several
writers run. A HammerDB schema build at WARE=10 with 4 loaders does not
complete; v0.4.1 completes the same profile on the same host.

Ordinary OLTP is unaffected. Mitigation is to load with a single connection, or
use a client that retries on 1213 / 1180; the data is never wrong, the
transaction aborts cleanly.

This is the unpatched half of the same reservation behaviour the carried patch
addresses, and fixing it needs a design change in the engine rather than a
patch. Full analysis, including why neither available workaround is acceptable,
is in [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

**This is why criterion 6 is reported at WARE=1 rather than the WARE=10 profile
the plan specified.**

## Methodology note

Three of the four contract changes were found by *running* the engine, not by
reading its headers — and the leak was found only because load validation ran
as a separate gate. The MTR suite was green at 87/87, the engine suite at
54/54, and every script-level gate passed, on a build that exhausted 12 GiB on
the smallest benchmark profile available.

A later audit of the v9/v10 header contracts for all 105 engine functions the
plugin calls rediscovered two of the four and found a third. It could not have
found the fourth: the abort-before-return behaviour lives in the
implementation's state transitions, not in the documented contract.
