# TidesDB v9.2.5 migration — validation report

**Date:** 2026-05-23
**Engine:** TidesDB **v9.2.5** + `docker/patches/0001-bloomfix.patch` (PR #626)
**Plugin/image:** `tidesdb/mysql:9.7` (MySQL 9.7.0, `ha_tidesdb.so` MODULE_ONLY)
**Scope:** validate the bump from vendored TidesDB v9.2.0 → v9.2.5, plus two new
test dimensions (engine-level integrity, tuned throughput).

## Environment

| | |
|---|---|
| Host | Linux 6.8, 20 logical CPUs, 62 GB RAM (~42 GB free) |
| Builder | Oracle Linux 9, gcc-toolset-14, CMake/Ninja |
| MySQL | 9.7.0 LTS (source build, plugin loaded as `ha_tidesdb.so`) |
| TidesDB | v9.2.5 (shallow clone of the upstream tag) |
| Carried patch | `0001-bloomfix.patch` — `bloom_filter_new` UAF null-out (PR #626) |
| Retired patch | `0001-walfix.patch` — all four bugs fixed upstream in v9.2.5 |

## Engine provenance

The four durability bugs we carried against v9.2.0 (`0001-walfix.patch`) were
each verified **fixed upstream in v9.2.5** and the patch was retired — applying
it now would re-break `FULL→NONE` because the sync-mode enum was reordered. The
remaining fix is the `bloom_filter_new` use-after-free (PR #626), still present
in v9.2.5, carried as `0001-bloomfix.patch`. Full per-bug detail and the
upstream-fix verification is in [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

## Test 1 — Crash-recovery (durability gate)

**What:** `bench/hammerdb/recovery-test.sh`. Build a TPC-C schema, run the
NewOrder mix, `docker kill -9` mid-write, restart on the **same** volume, and
verify committed work survived (post-restart orders per district ==
`d_next_o_id - 1`, no rollback). Engine in its safe mode (`sync_mode=FULL`).

**Profile:** WARE=10, RUNVU=4, 60 s pre-kill. `tidesdb_unified_memtable=OFF`.

**Result: PASS.** All 10 districts' `d_next_o_id` watermarks matched or exceeded
pre-kill (district 7: 3110 → 3111 — a NewOrder that committed in the kill window
survived). **Committed-row loss: NONE. Order-row gaps: NONE.** The upstream
fixes hold under the exact workload that originally exposed the four bugs.

## Test 2 — Engine integrity (mwbench, no MySQL)

**What:** new step. `docker/Dockerfile.mwbench` builds the upstream `mwbench`
tool against the exact engine source we ship (v9.2.5 + bloomfix);
`bench/mwbench/run-mwbench.sh` drives it. mwbench does a heavy sequential
ingest with concurrent reader threads that **byte-verify every value** read
back, then a delete → compact reclaim phase. This stresses the flush /
compaction / SSTable-cursor / bloom paths — where our bugs lived — with no
MySQL in the loop. PASS iff zero lost writes (`*_misses`, which already exclude
deliberately-deleted keys) and zero corruption (`mismatches`).

Wired into `run-all.sh` as a fail-fast **step 0**.

**Result: PASS.**

| profile | keys ingested | peak SSTables | misses | mismatches |
|---|---|---|---|---|
| `--quick` (~1 GiB) | 1,033,216 | 11 | 0 | 0 |
| 8 GiB, 64 MiB buffers | 8,260,352 | 88 | 0 | 0 |

The 8 GiB run drove 88 concurrent SSTables through L0→L1 compaction (the exact
pressure that exposed the cursor row-dropping bug) with no lost or corrupted
data.

## Test 3 — TPC-C throughput (tuned, DURABILITY OFF)

> **Not a durability test.** This profile disables per-commit fsync
> (`sync_mode=NONE`) to measure raw engine throughput, mirroring the
> methodology of tidesdb/hammer's `my.cnf.example`. For crash safety see Test 1.

**What:** `bench/hammerdb/run-throughput.sh`. Ports the reference benchmark
tuning (durability off, compression off, READ-COMMITTED, binlog/perf_schema off,
aligned cache budget) from MariaDB to MySQL 9.7, scaled from the reference's
128 GB / 32-thread box to this host. `tidesdb_unified_memtable=ON`.

**Tuning (this host):** `block_cache=4 GiB`, `unified_memtable_write_buffer=256 MiB`,
`max_memory_usage=8 GiB` (finite ceiling), `max_open_sstables=1024`,
`flush_threads=6`, `compaction_threads=4`; container 12 CPU / 32 GB.

**Result (TidesDB, durability off):**

| warehouses | run VUs | duration | NOPM | TPM | server |
|---|---|---|---|---|---|
| 40 | 16 | 3 min | 25,624 | 59,626 | stable |
| 100 | 16 | 5 min | 23,053 | 53,519 | stable |

Both runs completed with 0 handler-unsupported errors and no lost connections.

**Memory note:** the first WARE=100 attempt OOM-killed mysqld. The reference
config runs `max_memory_usage=0` (unbounded) with a 32 GB cache on a 128 GB box;
in a memory-capped container the unbounded engine plus 4096 open-SSTable
metadata grew past the cgroup limit. Fixed by giving the engine a **finite**
8 GiB ceiling (so it applies write backpressure instead of OOMing), a 4 GiB
cache, and `max_open_sstables=1024` inside a 32 GB container — validated at
WARE=40 before the full run.

## Reproduce

```bash
# durability gate
bench/hammerdb/recovery-test.sh

# engine integrity (build image once)
docker build -f docker/Dockerfile.mwbench -t tidesdb/mwbench:9.2.5 .
bench/mwbench/run-mwbench.sh                 # full 8 GiB gate
QUICK=1 bench/mwbench/run-mwbench.sh         # ~1 GiB smoke

# throughput (durability OFF)
bench/hammerdb/run-throughput.sh             # tidesdb, WARE=100
ENGINE=innodb bench/hammerdb/run-throughput.sh   # aligned InnoDB A/B
```

## Verdict

The v9.2.5 engine, with only the bloom UAF fix carried, **passes the durability
gate and the engine-level integrity gate**, and sustains a stable tuned TPC-C
throughput (~23k NOPM at 100 warehouses on this host). The migration is
validated for an experimental release.
