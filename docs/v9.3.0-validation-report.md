# TidesDB v9.3.0 engine bump — validation report (release v0.3.0)

Validation of bumping the bundled storage engine from **TidesDB v9.2.5** to
**v9.3.0** and shipping it **unpatched** (the `0001-bloomfix.patch` we carried
against v9.2.5 landed upstream verbatim in v9.3.0; `0001-walfix.patch` was
already retired at v9.2.5). Plugin changes: `TDB_ERR_BUSY` (-14) mapping and
the `default_l0_queue_stall_threshold` default lowered 20 → 10. See
[CHANGELOG.md](../CHANGELOG.md) and [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

### Investigation: a harness false-positive on first run

The **first** v9.3.0 run reported `point_misses=57 seek_misses=61
range_misses=0 mismatches=0` — a FAIL verdict. Root-caused to a defect in the
**mwbench harness** (built from upstream `master`), not the engine:

- All 118 misses appeared in a single ~5 s window at the delete-phase boundary
  (t≈65 s, long after ingest finished at t≈35 s) and then **plateaued** at
  57/61 through 150+ s of further random-sampled reads. `mismatches` stayed 0.
  Persistent data loss would keep getting re-hit and the count would climb;
  a plateau means a transient mis-classification, not lost data.
- `delete_phase_run` issued all deletes to the engine and **only then**
  published the deleted-set predicate (`g_del_step` / `g_del_total` /
  `g_del_max_key`). During the delete loop `g_del_step == 0`, so
  `pick_read_id`'s `expected_miss` (gated on `step > 0`) classified **no**
  deleted key as expected — every read of a just-deleted key was scored as a
  false data-loss miss.
- **Empirical confirmation:** re-running v9.3.0 with `--delete-fraction 0`
  (delete phase skipped) over the full 8 GiB / 8.26M keys produced
  `point_misses=0 seek_misses=0 mismatches=0` (`cum_miss=0/8260352`).
- The current mwbench `master` is API-coupled to v9.3.0 (it references
  `TDB_ERR_BUSY`, absent in v9.2.x — an `engine v9.2.5 + current harness`
  build fails to compile), so the older v9.2.5 mwbench image (which scored
  0/0) used an older harness without this delete phase and is not an
  apples-to-apples baseline.

**Fix:** `docker/patches/mwbench/0001-publish-delete-predicate-before-loop.patch`
(against pinned mwbench commit `d214ed83`) publishes the deletion predicate
*before* the delete loop. All inputs (`step`, `total_delete`, `max_key`) are
known up front; a not-yet-deleted key still reads as a hit (miss stays 0, value
still mismatch-checked) and an already-deleted key is correctly suppressed.
This is a test-tooling fix only — it does not touch the shipped engine. With
the fix, the gate returns a true 0/0 PASS with deletes enabled (above). To be
reported upstream to `tidesdb/mwbench`.

## Test 5 — 100 GiB mwbench engine stress (supplementary)

Two extended single-engine runs well beyond the release gates, to probe the
engine and harness at scale: target 100 GiB, 16 write / 8 read threads,
batch 512, 8 flush / 8 compaction threads, 256 MiB write buffer, 16 GiB block
cache, `l0-queue-stall-threshold=40`, `delete-fraction=0.05`. ~103.25M keys.
(Block cache auto-clamped to the engine's resolved memory limit ≈ 33.5 GiB,
half of host RAM — independent of fd budget.)

| Run | write-pattern | ingest | peak SSTs | peak disk | `cum_miss` | `cum_corrupt` | flush "ensure open" ERRORs |
|---|---|---|---|---|---|---|---|
| A | uniform | 341 s @ 300 MiB/s | 508 | 21.4 GiB (final; heavy overwrite dedup) | 0 | **0** | **189** |
| B | sequential, `--ulimit nofile=1048576` | 267 s @ 383 MiB/s | 687 | 198.9 GiB peak → 99.6 GiB settled (no dedup; transient ~2× during full merge) | 833 | **0** | **0** |

**Both runs: zero corruption (`cum_corrupt=0`), no OOM.** Two findings, both
**outside the shipped engine**:

1. **fd exhaustion (environment), not an engine bug.** Run A logged 189
   `ERROR: SSTable N failed to ensure open` (`tidesdb_sstable_write_from_memtable`,
   `TDB_ERR_IO`) in an ~11 s burst at peak SSTable count. Root cause: the
   container's default `ulimit -n = 1024` vs mwbench's default
   `--max-open-sstables = 65536` — at ~508 SSTables × ≥2 files each the process
   hit `EMFILE`, so a flush worker's `open()` failed. The engine's handle cache
   won't recycle aggressively when told it may hold 65536 open. **Fix:** raise
   the container fd limit (`--ulimit nofile=1048576`) or pass a realistic
   `--max-open-sstables`. Run B, with the fd limit raised, logged **zero** such
   errors. (This is why the shipped MySQL plugin defaults to a conservative
   `tidesdb_max_open_sstables=256`.)

2. **`cum_miss=833` in run B is a harness startup false-positive, not loss.**
   All 833 misses occurred in the **first ≤10 s of ingest** and then **froze at
   exactly 833** for the remaining ~1670 s (through the delete phase — the
   delete-predicate fix held, +0 there — and the full compaction). With 16
   sequential writers committing batches out of order at t=0, the harness's
   contiguous-committed-prefix estimate (`committed_prefix_end()`) briefly runs
   ahead of what is actually committed, so readers probe a claimed-but-not-yet-
   committed gap → transient not-found. Evidence it is not data loss: (a) the
   count never climbs as the keyspace grows (lost keys would be re-hit and
   accumulate); (b) `cum_corrupt=0`; (c) the 4-writer sequential gate (Test 2,
   8 GiB) scored 0/0 — the wider startup race only appears at 16 writers. This
   is a distinct harness limitation from the delete-phase one and is *not*
   covered by the carried patch; left as a documented artifact.

The `flush ordering violation` WARNs (1418 run A, 1659 run B) are benign
out-of-order-completion logging from 8 concurrent flush threads; `cum_corrupt=0`
confirms the LSM still reads correctly.

Run B's compaction phase ran ~2662 s (~44 min) — a single full merge of ~100
GiB of *unique* sequential data, with peak disk at 198.9 GiB (transient ~2×
write-amp holding merged output + inputs) settling back to 99.6 GiB once the
inputs were reclaimed. Total run ~3027 s. This is the cost of compacting a
non-deduplicating sequential keyspace at this size, not a stall (it progressed
throughout; `cq=1`, no backpressure).

> These runs are exploratory stress beyond the release gates and do not change
> the release verdict. Net: at 100 GiB the engine ingested ~103M keys with zero
> corruption and no OOM; the only errors were an fd-limit environment issue
> (fixed by raising `nofile`) and a harness startup-watermark false-positive.

## Verdict

**PASS.** All four gates green: MTR 61/61, mwbench 0/0 (deletes enabled), WAL
crash-recovery after SIGKILL, and WARE=100 throughput with no OOM. The engine
bump to TidesDB v9.3.0 shows no functional regression, no data loss or
corruption under stress, and durable crash recovery. The single initial FAIL
was a mwbench-harness false-positive (delete-predicate publish ordering),
root-caused, fixed in test tooling, and confirmed clean against the engine.
Cleared to ship as **v0.3.0**.
