# TidesDB v9.3.0 engine bump — validation report (release v0.3.0)

Validation of bumping the bundled storage engine from **TidesDB v9.2.5** to
**v9.3.0** and shipping it **unpatched** (the `0001-bloomfix.patch` we carried
against v9.2.5 landed upstream verbatim in v9.3.0; `0001-walfix.patch` was
already retired at v9.2.5). Plugin changes: `TDB_ERR_BUSY` (-14) mapping and
the `default_l0_queue_stall_threshold` default lowered 20 → 10. See
[CHANGELOG.md](../CHANGELOG.md) and [KNOWN-ISSUES.md](../KNOWN-ISSUES.md).

### Investigation: a harness false-positive on first run

The **first** v9.3.0 run reported `point_misses=57 seek_misses=61
range_misses=0 mismatches=0` — a FAIL verdict. Root-caused to a defect in the
**mwbench harness** (built from upstream `master`), not the engine:

- All 118 misses appeared in a single ~5 s window at the delete-phase boundary
  (t≈65 s, long after ingest finished at t≈35 s) and then **plateaued** at
  57/61 through 150+ s of further random-sampled reads. `mismatches` stayed 0.
  Persistent data loss would keep getting re-hit and the count would climb;
  a plateau means a transient mis-classification, not lost data.
- `delete_phase_run` issued all deletes to the engine and **only then**
  published the deleted-set predicate (`g_del_step` / `g_del_total` /
  `g_del_max_key`). During the delete loop `g_del_step == 0`, so
  `pick_read_id`'s `expected_miss` (gated on `step > 0`) classified **no**
  deleted key as expected — every read of a just-deleted key was scored as a
  false data-loss miss.
- **Empirical confirmation:** re-running v9.3.0 with `--delete-fraction 0`
  (delete phase skipped) over the full 8 GiB / 8.26M keys produced
  `point_misses=0 seek_misses=0 mismatches=0` (`cum_miss=0/8260352`).
- The current mwbench `master` is API-coupled to v9.3.0 (it references
  `TDB_ERR_BUSY`, absent in v9.2.x — an `engine v9.2.5 + current harness`
  build fails to compile), so the older v9.2.5 mwbench image (which scored
  0/0) used an older harness without this delete phase and is not an
  apples-to-apples baseline.

**Fix:** `docker/patches/mwbench/0001-publish-delete-predicate-before-loop.patch`
(against pinned mwbench commit `d214ed83`) publishes the deletion predicate
*before* the delete loop. All inputs (`step`, `total_delete`, `max_key`) are
known up front; a not-yet-deleted key still reads as a hit (miss stays 0, value
still mismatch-checked) and an already-deleted key is correctly suppressed.
This is a test-tooling fix only — it does not touch the shipped engine. With
the fix, the gate returns a true 0/0 PASS with deletes enabled (above). To be
reported upstream to `tidesdb/mwbench`.


**PASS.** mysqld restarted without manual repair; post-restart `d_next_o_id`
≥ pre-kill watermark for every district, orders rows == `d_next_o_id - 1`.

## Test 4 — HammerDB WARE=100 throughput

`bench/hammerdb/run-throughput.sh` (durability-OFF throughput profile; WARE=100,
BUILDVU=8, RUNVU=16, RAMP=2 min, DUR=5 min, 12 CPU / 32 GiB, block cache 4 GiB,
write buffer 256 MiB, `max_memory_usage` 8 GiB). v9.3.0's active-memtable
backpressure ceiling (2× write_buffer_size) bounds the unbounded growth behind
the OOM seen during v0.2.5 validation.

```
engine=tidesdb  WARE=100  buildvu=8  runvu=16  (unified_memtable=ON)
schema build      : COMPLETED
reverse-ref probe : PASS
throughput        : 22583 NOPM / 52572 MySQL TPM
OOM / kill events : 0
verdict: PASS -- schema built on TidesDB, TPC-C mix ran with no
         handler-unsupported errors
```

**PASS.** Comparable to v0.2.5's 23,053 NOPM / 53,519 TPM, but **with no OOM**:
the v0.2.5 WARE=100 run OOM-killed mysqld until mitigated with a finite memory
ceiling; under v9.3.0's active-memtable backpressure ceiling the same profile
ran clean to completion. (Throughput profile runs durability-OFF and is not a
persistence test; this exercises the unified-memtable path at scale but does
not re-validate the unified-path row-persistence question — see
[KNOWN-ISSUES.md](../KNOWN-ISSUES.md).)

## Verdict

**PASS.** All four gates green: MTR 61/61, mwbench 0/0 (deletes enabled), WAL
crash-recovery after SIGKILL, and WARE=100 throughput with no OOM. The engine
bump to TidesDB v9.3.0 shows no functional regression, no data loss or
corruption under stress, and durable crash recovery. The single initial FAIL
was a mwbench-harness false-positive (delete-predicate publish ordering),
root-caused, fixed in test tooling, and confirmed clean against the engine.
Cleared to ship as **v0.3.0**.
